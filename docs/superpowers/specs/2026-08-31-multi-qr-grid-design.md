# 多码网格传输 — 设计文档

- 日期：2026-08-31
- 状态：待审阅
- 分类：架构级（现有项目的功能扩展，跨发送端 + 接收端）

## 1. 目标与范围

在现有「纯二维码文件传输」基础上，把发送端「一次显示 1 张二维码」升级为「一次同时显示 2 或 4 张」，接收端从「一帧解 1 个码」升级为「一帧解多个码」，从而在**不提高单张二维码密度**的前提下提升有效吞吐，并适配手机横屏 / 竖屏两种拍摄姿势。

**范围**：

- 发送端：`FramePlayer` 网格渲染 + `MainFrame` 新增「张数」「排列方向」两个控件
- 接收端：`QrAnalyzer` 多码解码
- **协议完全不变**（见 §2），`FrameParser` / `Reassembler` / `TransferSession` / golden 向量一律不动

## 2. 核心思路（协议不变）

每张二维码仍然独立装一个块、自带 `chunkIndex`。多码网格只改变**呈现方式**（发送端同时显示几张）和**读取方式**（接收端一帧读几个），不改变任何帧的字节格式。

因此：

- 发送端与接收端**可以独立升级**——旧接收端扫新发送端，仍能逐张扫到（只是不知道网格布局，扫到哪张是哪张）；新接收端扫旧发送端，一帧只解到 1 个码，行为回退到单码。
- 接收端不关心网格内二维码的**排列顺序**：每个 `chunkIndex` 自描述，`Reassembler` 乱序去重收集。

## 3. 网格模型

引入「屏」（screen）概念，把原来的帧序列 `[METADATA, DATA_0, …, DATA_{N-1}]` 重排为「屏序列」：

```
屏 0： [METADATA]                                  （单张，居中放大）
屏 1： [DATA_0, DATA_1]        （gridSize=2）
       [DATA_0 .. DATA_3]      （gridSize=4）
屏 k： [DATA_{(k-1)·g} .. DATA_{k·g-1}]
...
最后一屏：剩余不足 g 的块（可能 1 ~ g-1 张）
```

- `gridSize` ∈ {2, 4}，用户可选
- 屏数 = `1 + ceil(totalChunks / gridSize)`（1 是元数据屏）
- 屏内块索引顺序：**行优先，从上到下、从左到右**

### 3.1 排列方向（layout）

`layout` ∈ {HORIZONTAL, VERTICAL, SQUARE}，用户可选，默认 `SQUARE`：

| layout | gridSize=2 | gridSize=4 |
|--------|-----------|-----------|
| HORIZONTAL（横向） | 1×2 单行 | 1×4 单行 |
| VERTICAL（纵向） | 2×1 单列 | 4×1 单列 |
| SQUARE（方阵） | 退化为 HORIZONTAL（1×2） | 2×2 |

## 4. 发送端改动

### 4.1 `FramePlayer`

| 变更 | 说明 |
|------|------|
| 新增字段 | `int gridSize`（默认 4）、`Layout layout`（默认 SQUARE） |
| 状态模型 | 由「单帧索引」改为「屏索引」；内存中只持有**当前屏**的 `List<BufferedImage>`（1 或 g 张），其余屏不预渲染（保持懒渲染、内存有界，与原设计一致） |
| `advance()` | 屏索引 +1（跳过一个屏，而非一块），取模循环 |
| `renderCurrent()` | 渲染当前屏：元数据屏渲染 1 张；数据屏渲染 g 张（最后一屏按实际剩余块数） |
| `paintComponent()` | 按 `layout` 把当前屏的多张图排布绘制（横向 1×g / 纵向 g×1 / 方阵 2×2），每张等比缩放到各自格子内、四周留静区 |
| 新增 API | `setGridSize(int)`、`setLayout(Layout)`：改后立即重渲染当前屏，可传输中实时切换 |
| 保留 API | `showChunk(int)` / `showMetadata()` **仍渲染单张全屏**（补漏模式，不套网格） |
| `currentLabel()` | 网格模式返回「屏 X：块 a~b」；单张模式返回「块 N」/「元数据」 |

布局枚举建议新增 `Layout`（HORIZONTAL / VERTICAL / SQUARE），独立于 `GridBagLayout`，放在 `ui` 包内。

### 4.2 `MainFrame`

- 「传输控制」面板新增两个下拉框，与帧率、尺寸并列，可传输中实时改：
  - **张数**：`2 / 4`
  - **排列方向**：`横向 / 纵向 / 方阵`
- 状态显示：`当前: 屏 X / 共 Y 屏`（单张补漏时回退显示「块 N / 元数据」）
- 块大小 `chunkSizeBox` 默认值由 512 改为 **256**（网格把每张二维码缩小到约半屏，256 是可靠甜点；三档 256/512/1024 仍全部保留可调）

## 5. 接收端改动

### 5.1 `QrAnalyzer`

| 变更 | 说明 |
|------|------|
| 多码解码 | 将现有 `MultiFormatReader` 外包一层 ZXing `GenericMultipleBarcodeReader`（`com.google.zxing.multi`） |
| 读取方式 | `analyze()` 改调 `decodeMultiple(new BinaryBitmap(new HybridBinarizer(source)))`，返回 `Result[]` |
| 逐码处理 | 遍历 `Result[]`，对每个 `Result` 沿用现有 ISO-8859-1 逻辑还原字节，逐个 `listener.onFrame(bytes)` |
| 保持不变 | `luminance()`（含 rowStride）、Y 平面提取、`DecodeHintType` 集合（仅 QR + ISO-8859-1）、异常吞掉 |
| 明确不加 | `PURE_BARCODE`（已实验：跳过定位导致真实画面解不出，回退）；`TRY_HARDER` 暂不加（观望） |

`MainActivity` 需设 `setTargetResolution(new Size(1920, 1080))`（本分支已含此改动；否则默认 640×480 在网格下每块模块过少、扫不动）；`TransferSession` 的 `onFrame` 天然支持连续喂多个块。

### 5.2 横竖屏适配（接收端）

**无需任何旋转处理**：QR 码对方向不敏感（ZXing 靠三个定位角找码，转 90°/180° 照样解），因此手机横拿竖拿都能解，无需 `setTargetRotation`。横竖屏的视野差异由**发送端排列方向**解决（见 §6）。

## 6. 横竖屏适配（发送端）

发送端是横屏显示器，手机竖屏时镜头视野是窄竖条、横屏时是宽横条。通过「排列方向」让用户按自己的手机拿法选择：

| 手机拿法 | 选择 | 效果 |
|---------|------|------|
| 横屏（视野宽） | 横向 1×g | 二维码沿屏幕宽排开，一眼看全 |
| 竖屏（视野窄高） | 纵向 g×1 | 二维码沿屏幕高堆叠，竖屏视野覆盖 |
| 不确定 / 均衡 | 方阵 2×2 | 正方形，横竖屏各看到一部分 |

## 7. 错误处理与边界情况

| 场景 | 处理 |
|------|------|
| 一帧解到 0 个码 | 现有 try/catch 吞掉，忽略本帧 |
| 一帧解到多个相同 `chunkIndex` | `Reassembler` 现有去重逻辑兜底 |
| 网格中某张被手机视野切掉一半 | 该张解不出，其余张照常；`GenericMultipleBarcodeReader` 跳过找不到的码 |
| 最后一屏不足 g 块 | 只渲染实际剩余块数，按布局对齐（不满格留空） |
| `gridSize` 或 `layout` 传输中切换 | 立即重渲染当前屏，不中断轮播 |
| 网格模式下块大小过大（1024） | 不强制拦截，但 UI 默认 256 并保留提示；用户自行承担密度风险 |

## 8. 测试策略

**发送端（JUnit）**
- 新增「帧 → 屏」分组纯函数测试：给定 `totalChunks` + `gridSize`，验证屏数、每屏块索引、最后一屏部分块、元数据单独一屏、`ceil` 边界（整除 / 不整除）
- 布局枚举 → 网格坐标映射测试（1×2 / 2×1 / 1×4 / 4×1 / 2×2）

**接收端**
- `FrameParser` / `Reassembler` 既有单测不变（协议未动）
- 多码解码依赖相机 + ZXing，靠**真机手动验证**：一屏多码能同时扫到、乱序归位正确

**端到端（真机冒烟）**
- 发送端 2 张 / 4 张 × 三种排列方向，各扫一遍，确认收齐、SHA-256 通过、保存成功

## 9. 已知限制

- 网格不提高屏幕**物理总密度上限**（屏幕能承载的总模块数不变），收益来自「单张二维码更稀疏、更可靠」，有效吞吐约提升 2~3 倍，而非严格 g 倍。
- 网格缩小单张二维码，**必须**配合较小的块大小（默认 256）；块越大，网格收益越被密度抵消。
- 排列方向需用户手动按手机拿法选择（发送端无法感知手机方向，单向信道）。
